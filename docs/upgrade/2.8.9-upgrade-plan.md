## Branching and rollback model

Read this before running any checkpoint. It is what makes the plan resumable.

There is **one** integration branch, `BAH-5058`, created off `master` and already holding this plan document. Every checkpoint ends with a **commit onto that branch**, and the checkpoint's rollback is a recorded commit SHA, not a branch deletion.

```bash
# the branch already exists and already holds this document. just get onto it.
git -C /Users/vishalkarmalkar/IdeaProjects/bahmni/bahmni-reports switch BAH-5058

# at the end of every checkpoint, without exception
git -C /Users/vishalkarmalkar/IdeaProjects/bahmni/bahmni-reports add -A
git -C /Users/vishalkarmalkar/IdeaProjects/bahmni/bahmni-reports commit -m "CP<n>: <what changed>"
git -C /Users/vishalkarmalkar/IdeaProjects/bahmni/bahmni-reports rev-parse HEAD   # record this in the state block
```

Do not use `git switch -c` per checkpoint and do not roll back with `git branch -D`. With uncommitted edits, `git switch -` carries those edits onto the branch you land on and `git branch -D` then deletes a branch holding no commits, so the change survives a rollback that appears to have discarded it. Every rollback below is `git reset --hard <sha>` against the SHA recorded at the previous checkpoint. The floor is the plan commit `045c1f1`; never reset below it, because it holds this document.

Every checkpoint must end with `git status --porcelain` printing nothing except untracked paths you intend to leave. A dirty tree at a checkpoint boundary means the checkpoint is not finished.

## Approach and its condition

**Direct jump to 2.8.9, skipping 2.6 and 2.7, conditional on CP1 reaching a green baseline.**

The condition is not a formality. If CP1 cannot produce a green suite, switch to the incremental path via 2.7.9 described under Fallback, because attribution then becomes the only verification tool left.

What the direct jump rests on, stated at the strength the evidence actually supports:

1. `openmrs-api` is a test-scope dependency and main source contains no OpenMRS Java API usage, so the shipped WAR carries no OpenMRS code. Strong, and it survived adversarial review.
2. Both forced dependency changes on the path land **before** 2.8.9 and are unavoidable by any route: Testcontainers becomes mandatory at **2.6.0** and the Liquibase floor at **2.7.0**. An incremental hop meets both at the identical place, so it buys no reduction in forced work. Strong.
3. A probe at 2.8.9 rules out dependency-resolution and static-init breakage. **Narrow, and weaker than it first appeared.** See below.

### What the probe does not prove

A probe run before this plan compared the failing test set at 2.8.9 against the 2.5.7 control and found them identical. That comparison matched test **names**, not failure **causes**, and it was run against the red baseline, where 296 of 341 tests abort at construction on a missing config file, upstream of any OpenMRS code.

Re-examined by cause, the runs are **not** identical. `ReportAuthorizationTest.shouldInvokeCallOpenMRSWithGivenSessionId` fails as `NoClassDefFoundError: Could not initialize class OpenMRSAuthenticator$MockitoMock$446490964` at 2.5.7, and as `RuntimeException: Invoking the beforeTestMethod method on PowerMock test listener ... AnnotationEnabler failed`, caused by `MockitoException`, at 2.8.9. `MockitoException` occurrences: 0 at 2.5.7, 1 to 2 at 2.8.9.

Two consequences the rest of this plan is built around. First, 2.8.9 does change harness behaviour, which is why PowerMock removal is CP4 and precedes the version bump at CP5. Second, no behavioural claim about the ~296 masked tests at 2.8.9 exists, because they have never executed at 2.8.9. Only a green CP1 can produce one.

### What an incremental path would buy

An incremental path buys no reduction in dependency floors, because the Liquibase floor lands at 2.7.0 either way. It does buy **attribution**: if the suite goes red after the bump, a 2.6 then 2.7 then 2.8 path localises the cause to one release, whereas a direct jump leaves three releases of change undifferentiated. That is worth little against a green baseline and a great deal against a red one, which is exactly why the recommendation is conditional.

## Fallback

**Trigger.** Either CP1 cannot reach a green suite, or CP5 goes red and the cause cannot be localised to a specific change.

**Path.** Incremental via 2.7.9, then 2.8.9. Land on 2.7.9 first, run the suite, then move to 2.8.9. This does not avoid the Liquibase floor, which arrives at 2.7.0, so CP3 and CP6 apply unchanged. What it buys is attribution: a red suite after a single hop names the release responsible.

**What carries over.** CP1, CP2, CP3, CP4, CP6, CP7 and CP8 are all independent of which OpenMRS version you land on. Because every checkpoint commits onto one integration branch, they carry over as commits with no cherry-pick: roll back to the CP4 SHA and change only the version property. That is the bulk of the effort and none of it is lost.

**What is discarded.** The version property change alone.

**One caveat on exit criteria.** CP8's criterion "test count matches CP5 exactly" is unevaluable if CP5 never went green. On the fallback path, substitute the count from the last green checkpoint, which is CP4, and record the substitution.

**If CP9 fails on the embedded Tomcat**, stop at Java 17 and keep everything else. CP4 is identical for 17 and 21, so nothing is wasted.
