### Code review, and how much of it

The **Review tier** column above is the effort to ask for, and it is set by what the diff can silently break, not by its line count and not by what sounds safest. The tiers follow one rule: a diff that touches `src/main/java`, a CI workflow, a shell script under `package/`, or SQL gets high or max, because those can stay green while degrading something no test measures. A diff confined to `src/test/java` whose test count and test method names both match the previous commit gets medium, and may be skipped if that evidence is stated. CP4 is the worked example of the second case, and of getting the call wrong: a high-effort review of a 178-line test-only diff ran past 13 minutes with nothing to show, on a diff whose main risks the count and name checks had already closed. See [cp4-observed.md](evidence/cp4-observed.md).

**The mandatory review is one review, at the PR boundary.** Run it on `master..BAH-5058` before the PR, not once per checkpoint. Per-checkpoint reviews re-derive from scratch what the checkpoint already proved, and structurally cannot see interactions across checkpoints, which on this branch is where the real risk sits. Per-checkpoint reviews are still fine when a checkpoint's own tier says high, or when you want one; scope them to a file list and a specific question rather than handing over the whole diff.

Two costs to plan around: the review agent starts with none of the session's context, and it reports all-or-nothing with no progress signal, so a long run buys nothing until it ends.

There is **one** integration branch, `BAH-5058`, created off `master` and already holding this plan document. Every checkpoint ends with a **commit onto that branch**, and the checkpoint's rollback is a recorded commit SHA, not a branch deletion.

```bash
# the branch already exists and already holds this document. just get onto it.
git -C /Users/vishalkarmalkar/IdeaProjects/bahmni/bahmni-reports switch BAH-5058

# at the end of every checkpoint, without exception
git -C /Users/vishalkarmalkar/IdeaProjects/bahmni/bahmni-reports add -A
git -C /Users/vishalkarmalkar/IdeaProjects/bahmni/bahmni-reports commit -m "CP<n>: <what changed>"
git -C /Users/vishalkarmalkar/IdeaProjects/bahmni/bahmni-reports rev-parse HEAD   # record this in the state block
```

Do not use `git switch -c` per checkpoint and do not roll back with `git branch -D`. With uncommitted edits, `git switch -` carries those edits onto the branch you land on and `git branch -D` then deletes a branch holding no commits, so the change survives a rollback that appears to have discarded it. Every rollback below is `git reset --hard <sha>` against the SHA recorded at the previous checkpoint. The floor is the plan commit `045c1f1`; never reset below it, because it holds this document.

Every checkpoint must end with `git status --porcelain` printing nothing except untracked paths you intend to leave. A dirty tree at a checkpoint boundary means the checkpoint is not finished.

### CP6. Repair the liquibase startup path

**Model: Sonnet.** One shell script. The trap is documented, including why the obvious glob fix does not work in POSIX sh, so this is careful editing rather than judgement.

Goal: the packaged container still runs its migrations.

```bash
cd /Users/vishalkarmalkar/IdeaProjects/bahmni/bahmni-reports
export JAVA_HOME=/Users/vishalkarmalkar/Library/Java/JavaVirtualMachines/ms-11.0.28/Contents/Home

# run-liquibase.sh:7,9 pin jar filenames exactly. Derive them instead. Note the script is
# #!/bin/sh and builds a colon-joined CLASSPATH, so a glob inside the assignment does NOT
# work: assignment does not glob-expand, and the joined word later matches no path and stays

# Derive with ls or find, one jar at a time, and fail loudly if either is missing:
#   LIQUIBASE_JAR=$(ls ${WAR_DIRECTORY}/WEB-INF/lib/liquibase-core-*.jar 2>/dev/null | head -1)
```

- Every derived jar path is guarded by a `[ -f ... ] ||` check that exits non-zero when missing. Grep alone is **not** an acceptable exit criterion here: it passes on the broken glob form too.
- The script runs to completion against a **scratch** MySQL database, exits 0, and `liquibasechangelog` is populated for both changelogs. This is the criterion that actually matters.
- `docker build` succeeds.

### CP7. Verify the reports against a real OpenMRS 2.8.x database

**Model: Opus.** Reading a schema diff and deciding whether each difference matters to 38 SQL files. This is the largest risk in the plan and it is genuine judgement.

Goal: evidence that the SQL still returns correct results against the schema the service will actually meet, captured as durable, rerunnable checks rather than a one-time manual pass.

**Scope decision, made explicitly rather than left implicit:** this checkpoint produces two durable artifacts, not just a one-time verification. Building full per-report correctness assertions (exact expected row values against a known-seeded dataset, for all 38 reports) was considered and explicitly deferred as a project-sized effort of its own -- raise it separately if wanted. What CP7 does commit to:

1. **Replace** `src/test/resources/sql/openmrs_schema.sql` with a schema captured from a real OpenMRS 2.8.x instance, rather than diffing it against the hand-patched fixture and discarding the real one. CP1 and CP5 both patched that fixture piecemeal, column by column, only when Hibernate happened to trip over a gap -- a real capture closes that whole class of gap in one step, and every one of the 341 existing tests keeps exercising the true 2.8.x shape going forward, in CI, for free. Re-verify CP1's and CP5's patches are subsumed (`edit_privilege`/`view_privilege`/`delete_privilege` on `global_property`, and whatever CP1's evidence lists) rather than assuming it.
2. **Automate** the "run each of the 38 reports, check the result" step as a smoke test committed to the suite (assert non-empty result set and no SQL error per report), instead of a human eyeballing output once. This is exactly the existing exit criterion below, wired into the suite rather than run by hand and discarded.

Parallelizable with: CP3 through CP6, once the distro question in Known unknowns is answered. It cannot start before that, because there is no target schema to test against.

This is the largest residual risk in the plan and no pom change touches it. The SQL bypasses the OpenMRS API, and `start.sh:11` applies this service's changelog to the OpenMRS database.

```bash
cd /Users/vishalkarmalkar/IdeaProjects/bahmni/bahmni-reports
ls src/main/resources/sql/*.sql | wc -l                    # 38
find src/main/resources -name '*.sql' | wc -l              # 40

# The two extra files under find are NOT OpenMRS queries:
#   sql/quartz/tables_mysql_innodb.sql  quartz DDL, applied to the reports DB by create_db.sh:8,25
#   sql/helper/patientAttributes.sql    a fragment
# Scope this checkpoint to the 38.

# 1. Stand up OpenMRS 2.5.7 and the target 2.8.x, let each build its schema.
# 2. Dump both schemas and diff them.
mysqldump --no-data -uroot -proot openmrs_257 > /tmp/schema-257.sql
mysqldump --no-data -uroot -proot openmrs_28x > /tmp/schema-28x.sql
diff /tmp/schema-257.sql /tmp/schema-28x.sql > /tmp/schema-diff.txt; wc -l /tmp/schema-diff.txt

# 3. Extract the tables and columns the 38 files reference, and intersect with the diff.
grep -ohiE '\b(from|join)\s+[a-z_][a-z0-9_]*' src/main/resources/sql/*.sql \
  | awk '{print tolower($2)}' | sort -u > /tmp/tables-used.txt
wc -l /tmp/tables-used.txt
while read -r t; do grep -q "\`$t\`" /tmp/schema-diff.txt && echo "CHANGED: $t"; done < /tmp/tables-used.txt

# 4. Replace openmrs_schema.sql with a --no-data dump of the 2.8.x schema (adapted to this
#    fixture's existing conventions, e.g. InnoDB/utf8 as already used). Re-run the full
#    suite against it; reconcile anything CP1/CP5's patches covered that the real schema
#    shapes differently.
# 5. Add a smoke-test class that iterates src/main/resources/sql/*.sql, runs each against
#    the (now-real-shaped) test database, and asserts a non-empty result set with no SQL
#    error. This is CP7's own former manual step, made permanent.
# 6. Apply both changelogs to a scratch copy of the 2.8.x OpenMRS database.
```

Exit criteria:

- `/tmp/schema-diff.txt` produced and non-empty, proving the two schemas were actually compared. An empty diff means the two databases are the same version and the comparison did not happen.
- `/tmp/tables-used.txt` is non-empty, and the intersection loop above has been run. Every `CHANGED:` line is either shown irrelevant in writing or fixed in the SQL.
- `openmrs_schema.sql` is replaced with a capture from the real 2.8.x instance, and the full suite (341+ tests) is green against it.
- A committed smoke test runs each of the 38 reports and asserts a **non-empty** result set with no SQL error, as part of `./mvnw clean test`. No report needs manual eyeballing to reverify this on a future run.
- The `person_attribute_type.format = "org.openmrs.Concept"` and `program_attribute_type.datatype = "org.openmrs.customdatatype.datatype.DateDatatype"` comparisons return rows, proving those literals still match live data.
- Both changelogs apply cleanly to a scratch 2.8.x OpenMRS database.

## Fallback

**Trigger.** CP5 goes red and the cause cannot be localised to a specific change. (CP1 already reached a green suite, so that original trigger no longer applies.)

**Path.** Incremental via 2.7.9, then 2.8.9. Land on 2.7.9 first, run the suite, then move to 2.8.9. This does not avoid the Liquibase floor, which arrives at 2.7.0, so CP3 and CP6 apply unchanged. What it buys is attribution: a red suite after a single hop names the release responsible.

**What carries over.** CP1 through CP8 are all independent of which OpenMRS version you land on. From CP3 onward, every checkpoint commits onto `BAH-5058`, so they carry over as commits with no cherry-pick: roll back to the CP4 SHA and change only the version property. (CP1/CP2 shipped separately as PR #106, already merged to `master` by the time CP5 would run, so they are not part of this rollback chain at all.) That is the bulk of the effort and none of it is lost.

**What is discarded.** The version property change alone.

**One caveat on exit criteria.** CP8's criterion "test count matches CP5 exactly" is unevaluable if CP5 never went green. On the fallback path, substitute the count from the last green checkpoint, which is CP4, and record the substitution.

**If CP9 fails on the embedded Tomcat**, stop at Java 17 and keep everything else. CP4 is identical for 17 and 21, so nothing is wasted.
